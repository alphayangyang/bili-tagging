# 个性化弹幕语义过滤系统

**Product Requirements & Technical Design — Draft v0.1**

状态：概念设计 / 原型验证前

> 来源：用户提供的早期笔记（AI 整理），原样存档。
> 与课程 slides、现有实现的对齐意见与收敛决策见 [reconciliation.md](reconciliation.md)。

## 1. 产品概述

### 1.1 产品定位

本项目旨在开发一个面向视频平台的**用户侧、语义感知、可解释且高度个性化的弹幕过滤系统**。

与传统关键词屏蔽及平台级内容审核不同，本系统不试图建立一套适用于所有用户的统一审核标准。

系统的主要任务分为两部分：

1. **Semantic Understanding（语义理解）**：利用 LLM、规则及上下文信息，将原始弹幕转换为结构化、多标签的语义表示。
2. **Personalized Presentation（个性化呈现）**：根据用户偏好和弹幕密度，决定哪些弹幕应显示、隐藏或折叠。

两部分通过中间表示解耦，避免直接将模型的语义判断等同于内容审核决策。

### 1.2 核心设计原则

**原则一：分类不等于审核。**

一条弹幕可以被识别为“讽刺”“幽默”甚至“攻击”，但不意味着它应当被自动删除。内容如何呈现，最终取决于用户的设置。

**原则二：语义标签不互斥。**

弹幕可能同时具有多种社会功能。系统应允许同一条弹幕匹配多个标签，并分别估计其符合程度。

**原则三：承认语义的不确定性。**

弹幕可能存在歧义、反讽或社群内部语境，不能假设任何人类或 AI 分类器都能永远给出唯一正确的解释。

**原则四：用户拥有最终控制权。**

插件可以提供默认策略与设置建议，但应当允许用户检查、修改和覆盖系统的判断。

**原则五：过滤不能创造内容。**

过滤器只能选择已有弹幕，无法保证过滤后仍然存在足够多的符合偏好的内容。因此，过滤精度和弹幕密度之间存在天然的权衡。

## 2. 问题定义

### 2.1 传统过滤方式的不足

**A. 全部显示 / 全部关闭**

现有的二元控制过于粗糙。用户可能只希望移除剧透、重复刷屏或攻击性弹幕，而继续保留解释、幽默与情感互动。

**B. 关键词过滤**

关键词匹配只能识别特定文本模式，存在以下问题：

- 对上下文和反讽理解能力不足；
- 新流行语、谐音、缩写和变体可能绕过过滤；
- 相同关键词在不同语境中可能具有不同含义；
- 用户需要不断维护关键词列表。

**C. 正则表达式与规则系统**

正则表达式可以提高模式匹配的灵活性，但难以完整处理语义歧义，且复杂规则的配置和维护成本较高。

**D. 平台级内容审核**

平台审核主要依据平台统一的内容管理标准。即使使用语义模型，也不一定向终端用户开放完整的分类依据和个性化决策能力。

因此，核心问题不只是提高审核分类器的准确率，而是：

**如何以可接受的用户负担与计算成本，让观看者自主控制弹幕的语义组成和呈现密度？**

### 2.2 研究问题

- RQ1：不同弹幕类型如何影响观看体验？
- RQ2：弹幕数量与类型之间是否存在交互效应？
- RQ3：基于语义标签的个性化过滤能否改善用户的控制感与观看体验？
- RQ4：分类精度、用户操作成本、弹幕密度和计算成本之间应该如何权衡？

这些均属于待研究和验证的问题，不预设肯定答案。

## 3. 目标用户与典型场景

### 3.1 目标用户

主要面向希望保留弹幕互动，又对弹幕内容具有明确偏好的视频观看者。

典型用户可能包括：

- 希望屏蔽剧透、保留剧情讨论的影视观众；
- 希望保留知识性补充、减少无关刷屏的教学视频观众；
- 希望保留玩梗氛围、减少争吵和攻击的游戏观众；
- 希望主动调整弹幕密度的普通用户。

这些用户类型是初步场景假设，需要通过用户研究验证。

### 3.2 核心使用场景

以游戏视频为例：

某用户希望保留幽默弹幕、允许一定程度的讽刺、隐藏严重的人身攻击，并避免过密的弹幕遮挡游戏画面。

传统过滤器很难通过简单的关键词规则表达这样的需求。

本系统允许用户直接配置语义类别和显示策略，并在播放时自动应用。

## 4. 产品功能设计

### 4.1 语义标签系统

系统首先将弹幕内容转换为一个**多标签中间表示（Multi-label Intermediate Representation）**。

初期使用预设语义类别：

| 标签 | 含义 |
|---|---|
| Information | 补充信息、解释、提示 |
| Humor | 玩笑、梗、幽默表达 |
| Emotional resonance | 情感表达、共鸣 |
| Repetition | 重复表达、刷屏 |
| Irrelevance | 与当前视频内容关系较弱 |
| Attack | 攻击、贬损 |
| Conflict | 争吵、对立性互动 |
| Spoiler | 剧情或结果剧透 |

此外，建议将 Sarcasm（讽刺）作为独立的辅助语义标签进行研究。

需要强调：这些标签不是天然互斥的，且不是所有标签都直接对应负面内容。

### 4.2 多标签评分

每条弹幕可以同时对应若干标签，每个标签具有独立的匹配分数。

例如，以下是假设性的模型输出：

`json
{
  "text": "你可真是个天才",
  "tags": {
    "humor": 0.70,
    "sarcasm": 0.85,
    "attack": 0.35
  }
}
`

这里的数值表示模型估计的语义符合程度，并不自动等于真实概率。

如果后续引入 Confidence（判断置信度）或 Uncertainty（不确定性），应当与标签符合程度分开定义。

这是一个重要的技术设计问题，需要在后续模型测试中确定。

### 4.3 个性化过滤策略

用户可以针对不同语义标签设置三种主要操作：

- **Show**：正常显示。
- **Hide**：隐藏该类弹幕。
- **Collapse**：折叠该类弹幕，允许用户主动展开。

过滤策略由用户设置决定，而不由分类器直接决定。

建议支持：

- 全局默认规则；
- 针对特定视频的临时规则；
- 各标签的匹配阈值；
- 过滤强度的整体调整；
- 恢复默认配置。

其中，前两项及阈值控制需要通过原型测试确定交互成本，不宜在初期提供过多复杂选项。

### 4.4 用户自定义语义标签

这是系统相对于固定分类器的一项潜在重要能力。

用户不仅能配置已有标签，还可以提出新的语义类别，例如：

- 特定角色相关剧透；
- 特定类型的无意义复读；
- 某个社群中的特定玩梗方式。

初步技术路线是允许用户通过自然语言描述和少量示例定义标签，并由 LLM 尝试进行泛化分类。

这样无需对所有新增标签都进行完整的人工重标注和模型重训练。

但是，自定义标签的跨场景泛化效果与计算成本仍需实验验证。

### 4.5 反馈与纠错

用户应能够：

1. 查看弹幕所对应的标签；
2. 理解它为何受到某条过滤规则影响；
3. 纠正明显错误的标签或过滤结果；
4. 调整后续过滤行为。

一个值得尝试的设计是：允许用户打开“已过滤弹幕记录”，或者查看折叠弹幕，从而纠正原本不可见的错误分类。

反馈可以在两个层次发挥作用：

- **策略层**：用户修改过滤偏好，立即改变呈现决策。
- **分类层**：用户纠正标签，作为后续分类改进的参考数据。

这两种反馈必须区分。改变偏好不必然意味着原来的语义分类是错误的。

### 4.6 弹幕密度控制（建议增加）

除了语义类型，原 PPT 还明确提出研究 Volume 对观看体验的影响。

因此，我建议把密度控制作为独立的产品模块，而不是完全依赖语义过滤的附带效果。

可探索的功能包括：

- 限制同一时间窗口内的弹幕数量；
- 对重复弹幕进行合并或折叠；
- 对不同语义类别设置呈现优先级；
- 允许用户调整整体弹幕密度。

关键约束：

**密度控制只能从已有弹幕中选择，不能创造原本不存在的互动内容。**

密度、用户偏好与视觉遮挡之间的权衡应当由用户实验指导，而不是直接假定某个固定阈值最优。

## 5. 系统总体架构

### 5.1 基本数据流

`text
视频弹幕数据
    │
    ▼
数据预处理
去重 / 清洗 / 时间戳整理
    │
    ▼
语义理解层
LLM + Rules + Context
    │
    ▼
多标签中间表示
Tags / Scores / Metadata
    │
    ▼
个性化决策层
用户偏好 / 阈值 / 冲突策略
    │
    ▼
密度与呈现控制层
显示 / 隐藏 / 折叠
    │
    ▼
浏览器插件渲染
    │
    ▼
用户反馈
`

### 5.2 语义理解层

主要负责从原始弹幕中提取社会功能和语义属性。

初步采用混合方案：

**LLM Prompting**

用于初始化标签分类器，尝试处理复杂语义、讽刺、网络用语与用户自定义类别。

**Rule-based Filtering**

用于处理明确且稳定的文本模式，减少部分不必要的模型调用。

**Context Awareness**

语义理解可能需要结合：

- 相邻时间窗口中的弹幕；
- 视频标题、分区与元数据；
- 当前视频片段或画面内容。

原型可以先采取文本优先的方式，再逐步研究增加上下文和多模态信息的收益。

### 5.3 中间表示层

这可能是整个架构中最重要的一层。

它将弹幕的语义理解结果与具体用户偏好分离。

理论上，同一段弹幕的通用语义分析可以被多个用户复用，而最终过滤策略在各用户端分别执行。

这种结构具有三个潜在优势：

- 用户改变过滤规则时，通常不需要重新训练模型。
- 通用语义结果可以缓存，减少重复推理。
- 用户能够检查标签，而不是只得到黑箱的 Keep / Remove 决策。

但需要注意：新增自定义标签、上下文变化或模型版本更新可能需要重新推理，因此缓存并不是永久有效的。

### 5.4 个性化决策层

对单条弹幕，决策层需要综合：

- 多标签匹配分数；
- 用户配置的标签策略；
- 各标签阈值；
- 标签冲突情况；
- 对不确定分类的处理规则。

一个尚待确定的问题是：如果一条弹幕同时属于用户希望显示和隐藏的类别，如何决定最终结果？

建议在原型阶段支持显式规则优先级，并研究保守折叠或允许用户覆盖的策略，而非简单假定所有场景都应该隐藏优先。

### 5.5 浏览器插件层

初期建议以浏览器扩展为原型载体，集中验证交互可行性。

主要职责是：

- 获取或接收弹幕数据；
- 加载语义标签及用户配置；
- 控制弹幕渲染；
- 提供设置、查看原因与反馈界面。

具体适配方式需根据目标平台的技术接口、服务条款和浏览器权限进一步确定。

## 6. 性能、成本与实际部署

### 6.1 核心工程问题

大模型推理存在延迟和成本，而弹幕可能在短时间内大量出现。

如果按用户、按弹幕逐条进行远程 LLM 调用，可能无法满足实际需求。

初步需要研究：

- 批量推理；
- 分类结果缓存；
- 视频弹幕预处理；
- 轻量模型与规则的协同；
- 延迟与成本之间的权衡。

### 6.2 可复用计算

对于预先存在的视频弹幕，可以考虑在播放之前或首次访问时批量生成通用语义标签。

后续用户使用已有标签执行个性化过滤，以减少重复推理。

但“本地插件”与“多用户共享缓存”并不能自动同时成立。

如果希望跨用户复用语义结果，可能需要额外的共享数据服务；如果坚持完全本地处理，则可以先实现同一设备上的缓存。

这是一个需要明确的架构决策。

### 6.3 不确定性与降级策略

模型不可用、标签缺失或推理超时时，系统应保留可预测的降级行为。

建议至少保证：

- 用户仍能正常观看视频；
- 已有缓存结果继续可用；
- 基础规则过滤可以独立运行；
- 不因语义服务错误而阻断正常弹幕渲染。

### 6.4 隐私与安全

如果弹幕、观看历史或用户偏好需要发送给远程 API，应清楚说明数据流向，尽量减少上传内容。

此外，弹幕文本本身属于不可信输入。进入 LLM 的文本不应被当作系统指令执行。

这些属于走向实际产品前必须补齐的工程要求。

## 7. 用户体验与评价体系

### 7.1 技术指标

**Precision**

在系统判定符合某类标签的弹幕中，有多少符合人工参考标准。

**Recall**

在参考标准标记为某类的弹幕中，模型找到了多少。

**F1 Score**

对 Precision 与 Recall 进行综合评价。

**Latency**

从获取弹幕到完成分类、得到显示决策所需的时间。

对于多标签系统，建议分别测量各标签的表现，再提供汇总指标。模型判断质量与最终过滤决策质量也应分开报告。

此外，实际部署还应关注单位弹幕处理成本、吞吐量和较高分位数的响应延迟。

### 7.2 用户体验指标

**操作成本**

- Setup Time：初始配置时间；
- Correction Count：用户需要纠正的错误数量；
- Workload：主观操作负担。

**观看体验**

- Discomfort：不适与干扰程度；
- Perceived Control：感受到的控制权；
- FOMO：担心错过有趣弹幕的程度；
- Co-viewing Feel：共同观看的社交氛围；
- Comprehension / Memory：信息类视频的理解与记忆表现。

这些指标共同服务于一个核心判断：

**更高的分类准确率是否真正带来了更好的观看体验？**

### 7.3 Ground Truth 与语义歧义

人工标注不等于绝对客观真理。

建议采用多位人工标注者建立参考数据，并记录一致性与分歧，对存在争议的样本进行复核。

对于明显存在多种合理解释的弹幕，不应强行消除全部分歧。

大型 LLM 或多模态模型可以作为辅助标注、分析上下文和定位疑难样本的工具，但不直接被视为无误的裁判。

对标签识别的评估与对用户偏好满足程度的评估，需要使用不同的判定标准。

### 7.4 实验设计建议

初期至少需要建立以下基线：

1. 原始弹幕（不进行过滤）。
2. 全部关闭。
3. 关键词或正则表达式过滤。
4. 基于语义标签的个性化过滤。

此外，建议通过独立实验分别考察：

- 不同弹幕类型和密度的交互效应；
- 语义分类能力本身的贡献；
- 个性化控制功能本身的贡献；
- 不同过滤强度对 FOMO、共同观看感和理解表现的影响。

实验中应控制或记录视频内容、参与者差异、遮挡和阅读负荷等潜在混杂因素。

## 8. 项目实施路线

### Phase 0 — 需求与研究准备

目标：明确用户的实际痛点，以及最值得研究的弹幕类别。

主要工作：

- 整理相关文献；
- 确定初始标签体系；
- 收集代表性弹幕样本；
- 明确研究问题和初步实验设计。

### Phase 1 — 最小可行原型（MVP）

目标：证明语义分类到个性化呈现的完整流程可以运行。

初期建议范围：

- 只支持一个视频平台；
- 优先支持已有弹幕的视频，而非直播；
- 使用有限的预设标签；
- 使用 LLM 为弹幕进行多标签分类；
- 实现 Show / Hide / Collapse；
- 支持基础用户配置。

MVP 阶段无需解决所有上下文歧义，也不需要保证高并发在线推理能力。

### Phase 2 — 语义质量验证

目标：验证分类体系的有效性。

工作包括：

- 建立人工参考数据；
- 比较 LLM、规则及可能的轻量分类器；
- 研究多标签输出与阈值；
- 分析反讽、流行语、标签冲突等困难样本；
- 测试上下文信息的作用。

### Phase 3 — 个性化交互

目标：验证用户是否能够低负担地表达和调整偏好。

增加：

- 用户反馈纠错；
- 更直观的过滤设置；
- 标签查看和过滤原因；
- 用户自定义类别的初步支持。

### Phase 4 — 密度控制与用户实验

目标：直接回答观看体验相关的研究问题。

增加弹幕密度控制，并在实验中比较不同过滤条件。

分析分类准确率、控制感、共同观看氛围与理解表现之间的关系。

### Phase 5 — 性能优化与实际部署

目标：研究系统的工程可扩展性。

重点解决：

- 缓存与批处理；
- 推理延迟；
- 模型成本；
- 上下文利用；
- 共享计算与本地部署方案。

## 9. 产品边界

本产品不承诺：

- 为所有弹幕提供唯一正确的语义解释；
- 彻底消除讽刺、歧义或社群内部表达造成的误判；
- 自动实现所有用户认为最好的观看体验；
- 在原始弹幕数量不足时创造社交氛围；
- 在原型阶段就具备大规模商业服务所需的吞吐量和成本水平。

本产品希望实现的是：

**在已有弹幕和有限计算资源的条件下，通过语义理解、可配置策略和用户反馈，为观看者提供比传统过滤方式更灵活、更透明的弹幕体验控制能力。**

## 10. 尚待确定的核心设计问题

以下内容不应假装已经解决，而应成为下一阶段设计与实验的重点。

**Q1：标签体系应该如何组织？**

采用固定的社会功能标签，还是允许用户自由创建任意标签？如何避免标签冲突和定义不一致？

**Q2：标签分数如何解释？**

语义匹配程度、模型置信度和用户过滤阈值如何分别定义与校准？

**Q3：过滤策略如何处理冲突与歧义？**

当多个标签对应相反操作时，系统如何决策？用户能否覆盖？

**Q4：用户偏好如何表达？**

复杂的逐标签设置提供了灵活性，但是否会造成过高的使用负担？

**Q5：如何处理弹幕密度？**

语义过滤、视觉遮挡、信息负荷与共同观看氛围之间存在什么关系？

**Q6：系统应该依赖多大程度的上下文？**

更多上下文可以提高理解能力，但会引入额外的计算成本和延迟。

**Q7：什么才是产品成功的标准？**

是分类准确率提高、用户操作减少、观看体验改善，还是若干目标之间的平衡？

## 11. 最终产品愿景

传统内容审核往往试图回答：

**“这条内容是否应该被允许出现？”**

本项目尝试回答一个不同的问题：

**“这条弹幕具有哪些语义属性，而当前观看者希望怎样处理它？”**

因此，系统的价值不仅在于过滤能力，还在于将语义解释与内容呈现决策分离。

它不需要假设所有用户共享一套审美和接受标准，也不需要承诺 AI 能完全理解自然语言。

最终希望建立的是一种**用户主导、AI 辅助、可解释且可调整的弹幕交互方式**。
